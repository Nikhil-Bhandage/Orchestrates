## 1. Mission

Build a reliable AI financial agent for the 250 requests in `requests.csv`.

The system must determine:

- safe amount to pay
- affordability status
- recommended payment method
- valid payment plan
- earliest date for full payment
- permitted spending changes
- concise, useful decision explanation

The goal is not to make the system maximally AI-heavy.

The goal is to combine:

- **AI** for understanding, ambiguity resolution and explanation
- **Python** for deterministic financial computation
- **DSA** for efficient data access and search
- **OCR/Vision** for image evidence
- **Validation** for financial safety and output correctness

Core principle:

> **AI understands. Algorithms calculate. Simulation proves. Validator enforces. AI explains.**

# 2. Non-Negotiable Design Rules

1. Read `AGENTS.md` before implementation.
2. Inspect the real repository and dataset before choosing exact structures.
3. Never let an LLM be the final authority for financial arithmetic.
4. Never write unvalidated LLM output directly to `output.csv`.
5. Never invent future income, expenses, payment options or evidence.
6. Never treat blank financial amounts as zero.
7. Never double-count the same financial event.
8. Never reduce protected/essential spending merely to make a purchase possible.
9. Use only payment options actually supplied by the dataset.
10. Optimize API/token usage by minimizing unnecessary AI calls.
11. Use DSA only where it improves real workload or correctness.
12. Prefer simple, testable architecture over unnecessary frameworks.
13. Preserve the required `log.txt` transcript; optimize its verbosity by keeping
    entries compact and avoiding duplicated bulk output, without omitting required turns.
14. Keep secrets out of code, logs, prompts, output and submission artifacts.

- financial state construction
- timeline construction
- forecasting
- plan generation

# 6. DSA Strategy

Use DSA deliberately.

## 6.1 Hashing

Use dictionaries/sets for:

- ID lookup
- duplicate detection
- grouping
- memoization
- cached AI/image results

Examples:

```text
events_by_id[event_id]
images_by_event[event_id]
seen_event_ids
ocr_cache[image_id]
```

Expected average lookup: `O(1)`.

---

## 6.2 Sorting

Sort each user's relevant events chronologically once.

Conceptually:

```text
events_by_user[user_id]
```

sorted by settlement/event date.

Sorting cost:

```text
O(E log E)
```

This enables efficient timeline processing and binary search.

---

## 6.3 Binary Search

Use `bisect_left` / `bisect_right` for:

- first event on/after a date
- first event after a deadline
- date-range boundaries
- locating timeline positions
- earliest affordable date where the affordability predicate is actually monotonic

Typical lookup:

```text
O(log E)
```

Do not force binary search if the predicate is not monotonic.

---

## 6.4 Prefix / Cumulative Sums

Where cash-flow aggregation is safe, maintain cumulative net changes:

```text
balance(t) =
    initial_balance
    + cumulative_inflows(t)
    - cumulative_outflows(t)
```

Then a date-based balance query can be approximately:

```text
binary search date -> O(log E)
prefix lookup      -> O(1)
```

Use a full simulator whenever state-dependent rules make a simple prefix sum
insufficient.

---

## 6.5 Sweep-Line / Two-Pointer Processing

For chronological intervals and recurring cash-flow windows, consider a
two-pointer/sweep approach instead of repeatedly rescanning the same events.

Example:

```text
sorted events
      +
sorted forecast dates
      |
      v
single forward pass
```

Potential complexity:

```text
O(E + D)
```

rather than:

```text
O(E * D)
```

where:

- `E` = relevant events
- `D` = forecast dates

Only use this when the actual data representation supports it.

---

## 6.6 Graphs

Use a graph representation where relationships between records matter.

A useful conceptual graph is:

```text
USER
 |
 +---- REQUEST
 |       |
 |       +---- PAYMENT_OPTION
 |       |
 |       +---- MESSAGE
 |       |
 |       +---- IMAGE
 |
 +---- FINANCIAL_EVENT
           |
           +---- LINKED_EVENT
```

Represent relationship edges using adjacency maps when useful:

```text
event_graph[event_id] = [linked_event_ids...]
request_graph[request_id] = [related IDs...]
```

Graph traversal can help:

- follow linked/amended/reversal relationships
- identify connected evidence
- prevent counting the same event through multiple representations
- isolate the relevant evidence subgraph for a request

Do not introduce graph algorithms merely for appearance.

For simple direct relationships, a dictionary may be faster and simpler than
a full graph class.

Potential graph algorithms:

- BFS/DFS for connected components or relationship traversal
- cycle detection if the dataset can contain cyclic links
- visited sets to avoid repeated traversal

Typical traversal:

```text
O(V + E)
```

for the traversed subgraph.

---

## 6.7 Memoization

Cache deterministic computations when identical inputs recur.

Potential caches:

```text
normalized_event_cache

candidate_simulation_cache[plan_signature]
ocr_cache[image_id]
llm_interpretation_cache[request_signature]
```

Only cache values whose inputs are fully represented by the cache key.

# 7. Duplicate Data and Event Identity

Deduplication must happen before financial calculations.

Do NOT blindly call:

```python
df.drop_duplicates()
```

on all financial records.

## 7.1 Primary Identity

Where `event_id` exists, treat it as the primary identity.

Use:

```text
events_by_id[event_id]
seen_event_ids
```

Do not count repeated representations of the same event twice.

---

## 7.2 Supporting Evidence Is Not a New Transaction

For:

```text
financial_events.csv
event_id = E123

messages.csv
related_event_id = E123

images.csv
related_event_id = E123
```

interpret this as:

```text
ONE financial event
+
supporting evidence
```

not three transactions.

---

## 7.3 Linked Events

`linked_event_id` does NOT automatically mean duplicate.

Inspect:

- status
- type
- amount
- date
- relationship
- cash effect

Follow the conflict-resolution rules in `AGENTS.md`.

Possible relationships include amendment, reversal or another legitimate linkage.

---

## 7.4 Possible Duplicate Records

If two records have different IDs but appear identical, compare:

- user
- date
- amount
- currency
- event type/category
- description/merchant
- status
- linkage

Only merge when dataset semantics justify it.

Never assume:

```text
same amount + same category = duplicate
```

because legitimate recurring transactions can have identical amounts.

---

## 7.5 Recurring Events Must Remain Separate

For example:

```text
Sep rent = 20,000
Oct rent = 20,000
Nov rent = 20,000
```

These are three real cash flows.

Deduplication must preserve them.

---

After resolution:

```text
canonical_events_by_user[user_id]
```

should contain the financial events that actually participate in calculations.

Keep supporting evidence attached separately.

For debugging, retain internally:


# 8. Event-State Resolution

Do not simply sum every row in `financial_events.csv`.

Handle:

- settled
- pending
- scheduled
- failed
- cancelled
- historical
- non-cash
- linked events

Follow `AGENTS.md` as the authoritative rule set.

Important:

- reserve pending debits where required
- do not treat pending credits as available cash
- count confirmed income according to settlement rules
- do not count unsupported future income
- do not count unrealized investment value as available cash
- avoid double counting

When interpretation is genuinely ambiguous, prefer the safer interpretation
required by the project rules.

Do not infer recurrence from one event.

Group by appropriate attributes such as:


Conceptually:

Do not invent future recurring events unsupported by the dataset.

# 13. Safe Amount

Do not use only:

```text
current_balance - minimum_balance
```

The safe amount must account for the forecast.

Conceptually:

```text
safe disposable amount at date t =
    available funds
    + confirmed inflows
    - committed expenses
    - projected essential expenses
    - minimum protected balance
```

Calculate over the relevant timeline.

The actual rules must follow `AGENTS.md`.

# 14. Plan Simulation

Implement:

```text
simulate_plan(financial_state, candidate_plan)
```

The simulator should:

1. Start from the correct available balance.
2. Process future events chronologically.
3. Process essential spending.
4. Process pending/committed cash effects as required.
5. Process proposed payments.
6. Update the balance.
7. Check minimum balance after every relevant event/payment.
8. Determine whether the request becomes fully paid.
9. Record completion date.
10. Return violation reasons if invalid.

Conceptual result:

```text
valid
final_balance
minimum_observed_balance
fully_paid
completion_date
violation_reason
```

A plan is invalid if it violates a hard financial constraint.

# 15. Candidate Plan Generation

```text
6. Not affordable
```

Do not invent payment options.

Do not generate a huge combinatorial search space when the supplied options

# 16. Hard Constraints vs Soft Preferences

This separation is mandatory.

## HARD CONSTRAINTS

Examples:

- balance never below minimum
- valid payment option
- installment limit
- protected spending preserved
- deadline requirements
- payment-plan format
- exact installment requirements
- partial-payment rules
- spending-change rules
- amount bounds

A hard-constraint violation means:

```text
candidate = INVALID
```

## SOFT PREFERENCES

Use only after safety filtering.

Examples:

- earlier completion
- fewer payments
- lower payment cost
- no spending changes
- preferred payment method
- user convenience

Architecture:

```text
candidate generation
        |
        v
hard constraint filter
        |
        v
safe candidates
        |
        v
preference ranking
        |
        v
best candidate
```

Never allow a high score to compensate for an unsafe plan.

Among valid candidates, rank deterministically.

Conceptual priority:

1. safe
2. satisfies deadline when possible
3. respects explicit user preferences
4. avoids unnecessary spending changes
5. completes earlier
6. uses fewer payments
7. minimizes additional payment cost

The exact ordering must be adapted to the official scoring/rules.

# 18. Earliest Affordable Date

The required date is the first date when the FULL requested amount can be
paid safely as one payment.

It is not the first date where some partial amount is available.

Potential algorithm:

```text
sorted timeline
       |
       v
identify relevant date range
       |
       v
binary search if affordability predicate is monotonic
       |
       v
validate candidate date with exact simulator
```

If the predicate is not monotonic because of future cash-flow behavior, use
event-based chronological simulation instead.

Never use binary search when its assumptions are invalid.

---

# 19. Partial Payments

Only allow partial payment when the official rules permit it.

Check:

- request permits partial payment
- user accepts/supports it
- safe amount > 0
- safe amount < requested amount
- full amount can be completed by required deadline
- exact required number of payments
- payment amounts sum to requested amount
- chronological feasibility
- minimum balance maintained throughout

Validate independently.

```text

  |

  |
  v

  |
  +---- low confidence ----> Vision AI
```

Use OCR for clean printed documents.

Use vision for:

- handwriting
- poor OCR
- complicated layouts
- semantic interpretation
- ambiguous monetary fields

Do not assume the largest number is the amount that matters.

Example conceptual extraction:

```json

  "currency": "INR",

```

Never interpret a blank amount as zero.

Cache:

```text

```

so the same image is not repeatedly processed.
